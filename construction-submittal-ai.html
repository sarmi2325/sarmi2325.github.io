Construction Submittal Compliance AI.

An AI document-intelligence platform that reads construction specification and product documents, matches submitted products against project requirements, and routes compliance decisions to the right reviewers.

Role: AI Engineer  ·  Focus: backend AI pipeline, reliability, evaluation
Industry: Construction / Enterprise AI  ·  Client: anonymized
Scroll to explore ↓

The problem

On large commercial projects, every product that gets installed must be checked against the project's written specifications before approval. Suppliers submit hundreds to thousands of product data sheets per project, and reviewers confirm each one by hand - slow, inconsistent between reviewers, and a frequent source of rework and schedule risk.

The solution

An event-driven platform that uses an LLM to extract structured requirements from specification PDFs, retrieves the relevant requirements per product with vector similarity search over PostgreSQL embeddings, and reasons about whether each product meets them.

Every item gets a verdict - compliant, non-compliant, or needs human review - and is routed by business unit to the reviewer who owns it. Large projects process in the background; approved products compile into a single reviewable package. The full pipeline is building alongside as you scroll →

What I did

  • Deterministic extraction. Made spec extraction reproducible so the same document yields the same requirement set on re-run - stabilizing every downstream verdict.
  • Distributed-systems correctness. Fixed a class of silent event-ordering bugs where events fired before their database transaction committed, by enforcing commit-before-publish.
  • No more stalls. Made the retry/failure cap effective, added completion guarantees so no item silently disappears, and a scheduled reconciler to recover stuck work.
  • Routing. Implemented business-unit routing of items to the right reviewer, with notification deduplication.
  • Evaluation & triage. Built parity/validation harnesses against known-good historical jobs, and triage tooling that labels each finding as a data-quality issue vs a real code bug.

Hardest problems

  • Non-deterministic extraction undermined trust. Re-running a document could change the requirement set, flipping verdicts. I traced the instability to extraction - not the matcher's judgment - and moved to extract-once-and-reuse.
  • A silent ordering bug stranded records. Handlers ran before data was committed, found nothing, and returned success with no retry. I recognized the pattern and enforced commit-before-publish.
  • Evaluating with no fixed ground truth. Parity harnesses against known-good jobs, treating a green diff as evidence about today's data only - then widening the validation set.
  • Data-quality vs code bugs. Many failures were malformed inputs, not defects. Triage tooling that labels each finding cut wasted debugging.

Results

  • Materially reduced verdict inconsistency on re-runs by removing non-determinism from extraction.
  • Eliminated a class of silent failures where items were stranded with no retry.
  • Removed indefinite pipeline stalls via an effective failure cap and a reconciler.
  • Cut debugging time by separating data-quality issues from genuine code defects.
  • Enabled reliable processing of projects with hundreds to thousands of line items.

What I took away

  • In production LLM systems, determinism and reproducibility matter as much as raw accuracy.
  • Most "AI bugs" are classic distributed-systems bugs - ordering, retries, idempotency - in an AI costume.
  • Evaluation is never finished: a green parity diff only describes today's data.
